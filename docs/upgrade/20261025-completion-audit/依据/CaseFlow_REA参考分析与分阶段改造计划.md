## 2. 用户已确定的目标和边界

主要实现以下能力：

1. 需求来源纳入项目知识库体系。
2. 生成前整理与测试目标相关的知识、公共条件及原文依据，能够检查采用了哪些资料、哪里仍有疑问。
3. 提取独立测试点，支持编辑和人工评审。
4. 用例追溯到测试点，再追溯到需求规则和原始文档。
5. AI 生成内容中的溯源链接可点击，精确打开对应版本的原文页码或段落，并高亮引用。
6. 基于可溯源依据生成详细用例，继续保留审核、导出、变更、历史与任务恢复。

用户允许取舍，不要求与参考产品完全一致。现阶段优先核心链路，暂缓完整专家平台、智能体连接、学习中心、复杂知识图谱及通用自动化执行。

“查找完整”应通过资料处理记录、规则清单和人工验收检查，不宣称 RAG 或模型能够保证语义无遗漏。

## 4. 当前 CaseFlow 的基础与主要差距

当前已具备资料导入、全文分段需求提取、澄清与冲突、规则确认、原文引用校验、生成与编辑审核、依据复核、数值规则、导出、需求变更、修订历史、人工执行结果、项目归档、任务恢复和调用预算。

技术基础包括 Vue、FastAPI、PostgreSQL、LangGraph，以及关键词、向量、混合检索和重排。继续复用，不因参考页面写了 LightRAG 就更换技术栈。

当前不足：

1. 有资料管理和底层索引，缺少统一、直观的项目知识入口。
2. 需求规则与用例之间没有独立测试点资源。
3. 生成前没有明确、可检查的依据准备结果；检索由模型按需调用。
4. 现有引用按钮打开提取文本，缺少可复制、可刷新、精确到段落的稳定链接。
5. CaseFlow 上传流程主要保存提取文本；建立检索时拼为 TXT，不能据此认定原 PDF 已持久保存并可原页查看。
6. 用例没有测试点编号与测试点修订关系。
7. 需要扩展依据复核上下文，纳入适用公共条件，不能仅因未关联某条规则就认定无依据。

进一步阅读入口（相对于当前独立仓库）：

- frontend/src/main.ts：实际入口加载 CaseFlow.vue。
- frontend/src/components/CaseFlow.vue：当前页面和原文查看方式。
- src/opslens/caseflow/api.py：API、任务输入、上传流程。
- src/opslens/caseflow/store.py：资料、连续引用、规则、用例、版本与审核。
- src/opslens/caseflow/agent.py：全文提取、工具、索引及生成编排。
- src/opslens/caseflow/grounding.py：依据复核和数值规则。
- src/opslens/rag/：文档、切分、检索与索引基础。
- docs/PRODUCT.md、docs/ARCHITECTURE.md、docs/VALIDATION.md、docs/EVALUATION.md：产品、架构、历史验证与真实模型观察。

历史记录曾观察到生成任务未调用 search_documents，不能写成每次生成都经过 RAG。模型依据复核使用同一配置模型的独立上下文，不是多个自主 Agent 保证正确。历史测试数量须按原日期和范围引用，不能写成本轮重新测试。

## 5. 五段实施计划

### 第 1 段：参考页面与证据清单

目标：整理“导入资料 → 提取测试点 → 人工评审 → 生成用例”的页面结构、可见状态和待验证行为。

工作：
- 逐张阅读 11 张图片，为核心页面建立入口、输入、按钮、输出、分组、筛选和引用展示清单。
- 每个结论记录图片文件名和证据类型。
- 区分图中可见状态与推测的转换，例如看到“待评审”和“通过”按钮，不等于已经观察到保存成功。
- 建立接口观察清单：触发操作、方法、路径、请求字段、响应字段、状态码、任务标识和进度通道；无证据时留空并标注未观察。
- 后续有网站或 HAR/SAZ，再使用 REA 补充对应记录和证据 ID，不覆盖原来的证据状态。

交付：参考页面分析、状态清单／转换草图、接口观察清单、待验证问题。

验收：截图事实与推测逐项分开；真实接口未观察的事实明确保留。现有图片足够回答的问题不重复询问用户。

### 第 2 段：CaseFlow 差距与最小实现设计

目标：把参考能力映射到当前源码，确定可实施方案。

工作：
- 检查仓库当前状态，核对实际前端入口、API、数据状态、生成、检索、复核、恢复和导出。
- 建立“参考能力 → 当前基础 → 缺口 → 复用／新增／暂缓”的映射。
- 明确资料、需求规则、测试点和用例的职责。
- 页面采用资料与知识、测试点评审、用例、需求更新；任务进度作为公共入口。
- 确定增量接口、任务、数据与版本关系，以及旧项目兼容方式。
- 结合既有三步优化计划：将原来的场景预览落实为测试点评审；复用库、回归计划和模拟执行仍放在后续。
- 新增设计和验收文档，不修改业务代码、数据库或模型配置。

交付：差距清单、页面草图、数据关系图、接口草案、兼容方案与验收清单。

验收：第 3—5 段可据此实施；不依赖猜测参考站的内部 API。不可从截图得知的事实继续标为未知。

### 第 3 段：知识资料与精确溯源

目标：实现 AI 产物中引用可准确回到原文。

工作：
- 复用现有存储和检索基础，建立项目内知识入口，暂不做跨项目共享。
- 保存原文件、解析快照和不可变文档版本；具体存储方案在第 2 段确定。
- PDF 按真实页码定位；Word、Markdown、TXT 按段落或文本区间定位，不编造 Word 物理页码。
- 程序根据已校验的位置生成稳定链接，模型只引用已有依据编号。
- 支持复制、刷新和重新打开定位链接，高亮连续原文；重复文字要有明确位置消歧。
- 展示资料用途、来源网址、解析提醒、版本与索引状态。
- 外部来源先保证导入快照内精确定位；可靠外部锚点另附，不猜测飞书段落链接。
- 新版本与旧版本并存，旧引用保持可打开。
- 旧资料没有原件时展示已有文本并提示，不伪装已保存原文件。

交付：资料列表、阅读面板、版本化引用与定位能力。

验收：引用跳转、刷新、复制、重复文字、跨页、文档更新和项目隔离均正确；历史资料与业务记录保留。

### 第 4 段：依据准备与测试点评审

目标：生成详细用例前，先形成可检查依据和独立测试点。

工作：
- 用户填写测试目标并选择资料范围。
- 明确执行依据准备，结合全文提取结果、知识目录、检索与原文回读，整理目标规则、公共条件、必要上下文及待澄清问题。
- 保存使用的资料版本和依据清单，展示未完成读取或不确定项；不把一次检索命中称为找全。
- 新增测试点：稳定编号、意图、场景分组、类型、模块、优先级、规则关系、原文依据、疑问、修订与审核记录。
- 场景先作为测试点分组，不另造一套重复的独立场景资源。
- 支持编辑、人工补充、筛选和批量通过／驳回。
- 分开显示引用位置校验、模型依据复核和人工评审。
- 标准流程主要评审测试点，规则草稿不伪装为人工已确认；保留现有严格确认流程。
- 明确冲突阻塞相关测试点，其他独立内容可继续；数值计算规则仍须明确确认。

拟实现状态：待评审 → 通过／驳回；已通过内容或依据变化 → 待复审。这是 CaseFlow 拟实现设计，不是参考站实测结论。

交付：依据准备结果、测试点资源与评审页面。

验收：没有有效依据的要求不能显示为已证实；待澄清与失效依据不能被批量操作绕过；任务恢复、预算与范围隔离继续有效。

### 第 5 段：用例展开与完整维护

目标：贯通“用例 → 测试点 → 规则／公共条件 → 原文版本与位置”。

工作：
- 仅按通过评审且依据有效的测试点展开详细用例，生成结果仍为草稿。
- 一次选择多个测试点，后台小批次处理，展示完成、失败、待处理项并支持续做。
- 用例保存测试点、规则和证据的修订关系；生成与复核共享适用依据。
- 继续保留用例编辑、设计审核和数值校验。
- 规则或资料变化后标记相关测试点及用例待复审。
- 导出增加测试点、规则、来源版本和定位链接；说明本地链接依赖 CaseFlow 服务运行。
- 保留旧编号、人工修改、旧修订和历史执行结果。
- 旧用例保留原“用例 → 需求 → 原文”关系，标明历史直接关联，不自动制造测试点或审核记录。

交付：完整主流程、导出、变更维护与验收记录。

验收：用预约上限 180 改为 120 分钟完成影响检查与新修订；旧来源和执行结果保留；断线恢复不重复保存用例。

## 6. 取舍与验证原则

紧随核心流程补齐模块、标签、优先级、测试目标输入和轻量统计。优先级沿用既有计划 P1/P2/P3，默认 P2，除非后续明确调整。

暂缓专家团队、人格／技能／记忆／MCP 平台、视频与题库、完整 Wiki 编辑系统、知识图谱、海量格式、超大文件和 OpenAPI 专用解析。接口说明可先作为资料；专用接口用例能力以后按需要增加。

真实执行测试、回归计划、问题与复测继续属于既有第二、第三步优化方向。本计划中的人工评审是测试设计评审，不能显示为业务测试已经通过。

验证分开记录：
- 工程检查：格式、引用、范围隔离、版本、状态、任务、恢复与预算。
- 页面验收：操作路径、按钮、定位、刷新、重复文字、批量与历史查看。
- 模型样本：关键测试点遗漏、无依据要求、重复内容及人工修改量。

使用固定预约资料和独立人工验收清单，不用模型输出自行证明模型正确。179/180/181 或 119/120/121 分钟仅是构造测试数据；仅满足时长规则不能推出预约整体成功。

保留首次失败、修复和复查记录；工程测试不能替代生成质量证据。优先受控响应及离线验证，不自动调用收费模型或改变用户模型设置。
